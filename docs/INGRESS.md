# Ingress, DNS, TLS

Every service reached under `https://<name>.passer.lan` takes the same
route:

```
LAN client
   │ resolve <name>.passer.lan
   ▼
Pi-hole (upstream DNS on the LAN)
   │ forward *.passer.lan (including the apex passer.lan)
   ▼
CoreDNS   192.168.178.241   (homelab-dns namespace, MetalLB)
   │ A record → 192.168.178.240
   ▼
Envoy Gateway   192.168.178.240   (envoy-gateway-system, MetalLB)
   │ HTTPS listener terminates TLS, HTTP listener redirects/serves
   │ HTTPRoute picks a backend by Host header
   ▼
Backend Service in the app's namespace
```

## Fixed IPs

| Endpoint                    | IP              | Owner                                                 |
|-----------------------------|-----------------|-------------------------------------------------------|
| Envoy Gateway               | 192.168.178.240 | MetalLB pool `lan-pool`, referenced by the Gateway CR |
| CoreDNS                     | 192.168.178.241 | MetalLB pool `lan-pool`, homelab-dns Service          |
| Velero backup target (MinIO)| 192.168.178.2   | `passer` Raspberry Pi                                 |

## The Gateway CR

`infrastructure/configs/gateway.yaml` defines:

- `GatewayClass envoy` (Envoy Gateway controller)
- `EnvoyProxy envoy-static-lb` — asks MetalLB for exactly `192.168.178.240`
- `Gateway envoy` in `envoy-gateway-system` with two listeners:
  - `http` on `:80`
  - `https` on `:443`, TLS terminate with `certificateRef` pointing at
    `passer-lan-tls` in the same namespace

`allowedRoutes.namespaces.from: All`, so HTTPRoutes anywhere in the
cluster can bind to it.

## HTTPRoute pattern

Every app's HTTPRoute binds both listeners so the same hostname works
for HTTP and HTTPS:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: <app>
  namespace: <app>
spec:
  parentRefs:
    - name: envoy
      namespace: envoy-gateway-system
      sectionName: http
    - name: envoy
      namespace: envoy-gateway-system
      sectionName: https
  hostnames:
    - <app>.passer.lan
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - name: <service>
          port: <port>
```

Several charts (Authentik, bjw-s-based ones) let you declare the same
HTTPRoute from the HelmRelease values under a `route:` / `service.route:`
block instead. See `apps/production/authentik-values.yaml` for an
example — the chart-created HTTPRoute is named `<release>-server` and
uses the same parentRefs.

## TLS

Self-signed, no ACME.

- CA + wildcard leaf are generated by `scripts/generate-passer-lan-cert.sh`
  and dropped into `secrets/` (gitignored).
- The leaf Secret is named `passer-lan-tls`. It is replicated into every
  namespace that references it via `scripts/apply-passer-lan-tls-secret.sh`
  — the Gateway itself needs it in `envoy-gateway-system`.
- **SANs:** `passer.lan` **and** `*.passer.lan`. The apex is covered,
  so the landing page at `passer.lan` uses the same cert as any
  subdomain.
- Trust it once per client machine: import `secrets/passer-lan.crt` into
  the OS/browser trust store. Every browser you don't do this in will
  warn.

## DNS

Two paths keep the DNS in sync:

1. **Static records in CoreDNS.** Some names are declared directly in
   the CoreDNS ConfigMap.
2. **ExternalDNS.** Watches HTTPRoutes and writes their `hostnames` as
   A records pointing at the Gateway address into CoreDNS via its
   ETCD backend.

Adding a new hostname is therefore just adding a new HTTPRoute — no
manual DNS entry.

**Pi-hole configuration** (on the LAN, outside the cluster): forward
`*.passer.lan` to `192.168.178.241`. This must include the apex; a
wildcard forward covers it.

## Troubleshooting

### `nslookup foo.passer.lan` fails on my laptop

1. Confirm Pi-hole is the LAN's DNS server (`resolvectl status` or
   `/etc/resolv.conf`).
2. Query CoreDNS directly to see whether the record exists:
   ```bash
   nslookup foo.passer.lan 192.168.178.241
   ```
3. If CoreDNS answers but Pi-hole doesn't, Pi-hole's forward rule for
   `passer.lan` is missing.
4. If CoreDNS doesn't answer either, the HTTPRoute doesn't exist yet,
   or external-dns is broken:
   ```bash
   kubectl -n external-dns logs deploy/external-dns --tail=50
   ```

### DNS is fine but I get 404

The HTTPRoute isn't bound to the Gateway, or points at a Service that
doesn't exist. Both show up in status:

```bash
kubectl -n <ns> describe httproute <name>
# look for: Accepted=True, ResolvedRefs=True
```

### DNS + routing are fine but the browser complains about the cert

You haven't trusted `secrets/passer-lan.crt` on that machine yet. For a
one-off probe:

```bash
curl -sk https://foo.passer.lan/
```

`-k` ignores TLS validation. `openssl s_client` can print the served
cert if you need to confirm SANs.
